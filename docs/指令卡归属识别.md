# 原生战斗的英灵与指令卡识别

规范依据：[MaaFramework Pipeline](https://maafw.com/docs/3.1-PipelineProtocol/)、[Custom & Agent](https://maafw.com/docs/1.3-Custom%26Agent/)、[ProjectInterface V2](https://maafw.com/docs/3.3-ProjectInterfaceV2/)。进本、技能点击、选卡与结算沿用原生自动战斗 pipeline，识别节点和图片资源统一放在 base。

原生战斗使用现有的 Chaldea 队伍配置读取攻略中的技能、出卡和敌方目标，不新增手动选怪、主输出或选卡倾向选项。

## 身份、技能与选卡流程

1. 进本时复用六槽初始编队快照。现有整幅头像匹配失败时，再尝试局部头像匹配。Chaldea 队伍提供另一份身份来源；同一位置两份证据冲突时保留未知。
2. 战斗主界面匹配当前三个位置的 HUD 头像，只搜索已确认的编队成员（含候补）。先确认从者存在，再识别其三个技能的 CD；未知位置按空位处理，不识别或使用该位置的从者技能。
3. 每次主界面观测更新当前前排，显式换人后同步阵容映射。HUD 头像匹配缓存已确认区域，画面变化时重新识别。
4. 点击 Attack 后由 `战斗_选卡展开等待` 等待上排宝具卡展开，再读取五张面卡、三处宝具区域及限制状态。
5. 面卡与宝具使用专用 command portrait，候选仅为当前前排身份的全部灵基和灵衣变体。缺少模板、同 ID 双前排、低分或候选分差不足时保留未知归属。
6. 优先执行 Chaldea 攻略中的出卡意图。未指定或缺失的面卡沿用原有通用补卡，优先选择可攻击面卡，再按既有卡色评分排序。

Chaldea 计划保留攻击记录中的英灵、卡色、敌方目标及面卡与宝具的混合顺序。敌方目标从 `options.enemyTarget` 转换为原生槽位，没有手动配置覆盖层。例如攻略的 `B → 宝具 → B` 会映射到当前截图中的真实位置。计划缺少的面卡或不可用宝具由普通面卡策略补齐，不重复选择同一张卡。攻略的 `card` 是英灵牌组索引，不是屏幕位置；同英灵同色面卡目前按画面从左到右匹配，不区分指令纹章或暴击率。攻略回合结束后恢复通用选卡。

## 宝具与封印

宝具是否可选由上排实际卡面及限制标记决定，**不读取 NP 百分比，不使用 NP 数值 OCR 判断可用性**。`NpCard.percent` 仅保留为历史快照的兼容字段。

- 头像确认失败时，需同时识别宝具名称和公共卡框；场景文字不能单独生成宝具卡。
- 被封印或无法行动的宝具不选择。
- 失效面卡优先避开；可攻击牌不足三张时，允许选择失效面卡占位以推进回合。

面卡头像使用 `TM_CCORR_NORMED`，门槛为分数 0.86、候选分差 0.05。宝具头像使用 `TM_CCOEFF_NORMED`、半分辨率及两段脸部区域，门槛为分数 0.80、候选分差 0.05，以减轻状态图标遮挡和明亮背景的干扰。匹配分数不是正确率。

## 离线资源维护

运行时不联网下载头像。资源来自 Atlas Academy 的 `NiceServant.extraAssets`：

| 资源目录 | 数据字段 | 用途 |
|---|---|---|
| `assets/resource/base/image/CommandCards/<servant_id>/` | `commands` | 面卡和宝具头像 |
| `assets/resource/base/image/ServantStatus/<servant_id>/` | `status` | 战斗 HUD 头像 |
| `assets/resource/base/image/battle/card_state/` | 游戏 UI 模板 | 封印、无法行动和宝具卡框 |

前两类各含 1562 张 PNG；`manifest` 记录来源 URL 和 SHA-256。维护清单不使用 `.json` 扩展名，避免被资源加载器当作 pipeline。限制状态模板的来源和修改见同目录 `SOURCE.txt`。

2026-10-21 对 `CommandCards` 进行压缩对比试用：保持 256×256 尺寸，不缩放、不裁剪，沿用从者头像的 Pillow FASTOCTREE 256 色、无抖动量化，并以 `optimize=True, compress_level=9` 保存 PNG。1,562 张图从 121,125,909 字节降至 28,896,419 字节，减少约 76.14%；原图和原清单另存于本地备份，不放入资源包。部署清单的 `sha256` 对应量化图，新增 `source_sha256` 保留原图哈希，`image_transform` 记录本次处理参数。全量图片的尺寸、解码与 `alpha >= 128` 匹配遮罩已校验；颜色量化并非无损，真实战斗识别效果仍需对照验证。本次未修改下载脚本，后续新下载或强制重新下载的原图仍需另行量化。

## 合成指令卡与压缩试验（未接入战斗识别）

2026-10-21 确认普通指令卡可以按游戏的 NGUI `CommandPrefab` 分层合成。早期对照图只保存到本地分析目录；用户确认后，另将所需公共图层及宝具名称作为新增素材放入 `CommandCards/_composition/`，提供独立调用模块。**不覆盖现有头像，不将整卡合成图预生成到正式资源，不改现有战斗识别流程**。

### 图层与透明度

- 从下到上依次为 `card_bg_<卡色>`、从者 command portrait、`card_icon_<卡色>`、`card_txt_<卡色>`。卡色分别为 `buster`、`arts`、`quick`。
- 公共素材使用 `CommandAtlas` 的 RGB 和 `CommandAtlas_alpha` 的红色通道合成 RGBA；二者使用相同 UV。已有拆分 PNG 的 Alpha 可能全部为 255，不能直接当作透明图层使用。
- 图层按普通 Alpha 混合叠加；头像不是根据卡色染色。原始素材、还原透明度的素材、合成图和量化图分别保留。
- 预制体保存值不等于实机最终值。以阿尔托莉雅（100100）的 1280×720 MAA 截图标定时，图组缩放约 1.25；头像局部尺寸取约 191×191，文字取素材尺寸 150×73，明显优于直接使用保存的 165×165、126×66。以上为同一截图拟合值，不是已解码确认的运行时参数。
- 本次预览其余局部参数：背景 133×170、位置 `(0, 0)`；头像位置 `(0, 6)`；图标 186×134、位置 `(4, -42)`；文字位置约 `(4, -47)`。坐标为局部 UI 单位，Y 轴向上，不能直接当作屏幕像素。

### 合成后再量化

合成完成后，对透明 RGBA 图执行 `image.quantize(colors=256, method=Image.Quantize.FASTOCTREE, dither=Image.Dither.NONE)`，以 PNG `optimize=True, compress_level=9` 保存。保持尺寸，不缩放、不裁剪；这是有损颜色量化，不是无损压缩。每次需检查可解码性、调色板数量、原图哈希以及 `alpha >= 128` 二值匹配遮罩是否改变。

同一张 1280×720 截图上的整卡对比结果如下。采用 OpenCV BGR 三通道 `TM_CCOEFF_NORMED`，以 `alpha >= 128` 作遮罩、去除透明外边距，在五张卡各自区域内搜索；所有版本固定尺寸，不再搜索缩放。

| 模板 | 预制体保存尺寸 | 实机标定合成图 | 合成后 256 色图 | 原图字节 | 量化图字节 |
|---|---:|---:|---:|---:|---:|
| Quick | 0.6111 | 0.9633 | 0.9602 | 76,400 | 19,889 |
| Buster | 0.6082 | 0.9602 | 0.9570 | 75,943 | 19,189 |
| Arts | 0.6839 | 0.9748 | 0.9718 | 76,087 | 19,028 |

三张合计从 228,430 字节降至 58,106 字节，减少 74.56%；匹配度各下降约 0.003，仍命中正确卡位，二值 Alpha 遮罩均未改变。量化规则可作为后续试验默认方案，但分数不是正确率，且标定与复测用了同一截图，不能据此认定其他从者、灵基、分辨率、动画、封印状态或宝具卡均已验证。以上为 OpenCV 离线复测，不是 MaaFramework pipeline 实测。

## 独立合成模块与素材组织

正式新增素材按资源包分开放置：日服默认在 `assets/resource/base/image/CommandCards/_composition/`，国服覆盖在 `assets/resource/cn/image/CommandCards/_composition/`。两处使用完全相同的相对路径和 FASTOCTREE 256 色无抖动 PNG：

- `shared/`：三色背景、宝具背景、色卡图标及文字，每个资源包各12张。国服恢复透明度并按图集 padding 补回裁剪前画布，不将紧裁小图拉伸到日服尺寸。
- `np/<servant_id>/card_servant_np.png`：256×256 宝具名称图，base 放日文，cn 放中文，同名覆盖。维护工具按现有头像清单补充，404 缺图记入该资源包清单；网络或解码错误不能当作缺图通过。
- `manifest`：每个包各自一份无扩展名清单，schema_version=2，`region` 标明地区，`shared`、`np_names`、`missing` 均只记录本包。包含来源、原图/压缩图 SHA-256、名称行及遮罩变化。`SOURCE.txt` 说明来源。不能把维护清单改成资源目录内的 `.json`。

名称图不放到现有 `<servant_id>/*.png` 目录，因为旧识别器会遍历那里所有 PNG；否则会误把文字当头像。现有 `CommandCards/manifest` 仍只管理原头像，新素材使用独立清单。

2026-10-21 首次入库：12 张公共图层、471 张 JP 名称及 453 张 CN 名称，共 936 张 PNG、7,079,452 字节（约 6.75 MiB）。随后补充12张国服图层，迁移后的 base 为483张、cn为465张，共948张；PNG内容未因迁移改变。源站明确返回404的18项国服名称记入 cn 的清单 `missing`，不使用JP图补位。全部图片已校验 P 模式、尺寸、解码及哈希，量化前后 `alpha >= 128` 遮罩均未变化。10 张名称图同时存在上下两行，其余914张只有上半行。

### Agent 直接调用

`agent/battle/card_composer.py` 不导入 Maa、Pillow、UnityPy 或解密库，不联网、不落盘，只依赖工程已有的 OpenCV 和 NumPy。返回 `ComposedCard`：`bgra` 为 uint8 BGRA 图，`bgr` 可用于匹配，`mask` 为与它严格对齐的 `alpha >= 128` 二值遮罩；图像只去掉遮罩外透明边距，`anchor` 记录裁后图中的图组原点。

```python
import cv2
from agent.battle.card_composer import CommandCardComposer
# Agent 自身把 agent/ 加入 sys.path 时，也可以 from battle.card_composer 导入。

composer = CommandCardComposer()  # 开发目录及打包 resource/base/image 路径自动查找
face = composer.compose(100100, "buster", portrait_variant=1)
cn_face = composer.compose(4000100, "arts", portrait_variant=3, region="CN")
noble = composer.compose(
    202200, "quick", portrait_variant=1,
    card_type="np", region="JP", np_name_row=0,
    viewport=(1280, 720),
)
scores = cv2.matchTemplate(
    screenshot_roi, noble.bgr, cv2.TM_CCOEFF_NORMED, mask=noble.mask,
)
```

由调用方提供实际从者 ID、灵基/灵衣图片变体编号、卡色及宝具名称行；模块不会猜当前宝具或使用替代头像。名称行 0 为上半图、1 为下半图，调用方需先确认对应关系，不能把行号等同于宝具等级或灵基阶段。宝具必须显式传地区；缺地区、缺图、空名称行、损坏图片及非 16:9 尺寸均明确报错，禁止跨地区退回日服。普通卡的地区支持 JP/CN，省略等同 JP；普通卡不接受非零宝具名称行。

`viewport` 是实际用于匹配的 MAA 截图尺寸，不是模拟器窗口尺寸；默认 1280×720，按截图高度相对 720p 等比缩放。布局为当前实验 profile `command-card-720p-v1`，并非所有动画/状态的精确复现。

标准开发与打包目录自动定位 base 根目录及对应兄弟地区目录。OpenCV读图时自行按“地区优先、base补充”查找，不依赖 Maa 自动覆盖。共用头像/卡框/图标可以回退base；国服普通卡文字和非JP宝具文字不能跨语言回退。自定义目录可调用 `CommandCardComposer(base_root, region_roots={"CN": cn_root})`，覆盖根目录必须指向 `image/CommandCards` 对应层级。多个同类根按传入顺序优先；地区始终高于base。

复用同一个 composer，首次生成后按身份、变体、卡色、卡类型、地区、名称行、分辨率缓存；默认最多 32 张、32 MiB，超过任一限制即淘汰旧项。每次返回独立数组，调用方修改不会污染缓存。资源更新后调用 `clear_cache()`；测试可用 `cache_info()` 查看条目和字节数。运行时无须量化，压缩用于缩小打包素材，不会直接减少解码后的内存占用。

本机 1280×720 的一次测量：单张首次生成约 15.7ms；三名前排的 9 张三色普通卡加 3 张 JP 宝具卡（12 张不同模板），清空 composer 缓存后 20 轮整组生成中位数约 139.6ms，缓存命中后 100 轮整组取图中位数约 1.8ms，缓存数组约 3.06 MiB。整组计时包含生成 `.bgr` 匹配输入，不包含 Python/库启动、PNG 导出、量化或模板匹配；系统磁盘缓存没有清空，安卓性能未实测。这是本机样本而非性能承诺；调用方应复用 composer，可在前排确定后预热，不能每帧重建实例。
