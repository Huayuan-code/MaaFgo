# 特殊技能选项批量补全与日服实机验证方案

## 2026-10-25 按战前实际编队缩小检测范围

特殊技能检测只在本场持有完整、已标定的实际编队快照时裁剪。六槽均须为已确认身份或明确空位，且与 Runtime 接收的合并队伍一致；包含助战和候补，不只看初始前排。入口 `战斗_特殊技能处理.attach.special_skill_servant_ids` 声明各分支所属的从者 ID，Runtime 按规范 ID 匹配，兼容目录声明的变身形态/别名；不使用名称判断，也不改变各分支原有优先级、默认选项、点击或等待。

没有快照（包括直接从战斗内启动）、部分身份未知、Chaldea 与实际编队冲突，或连续出击复用了未在本场重新确认的旧快照时，保留完整检测。Chaldea 预期队伍不能单独作为排除实际从者的依据。不新增战斗内全库身份扫描，也不改变直接从战斗启动时的现有技能决策行为。

通用的技能不可用弹窗、目标选择和无覆盖层终点始终保留；未声明所属从者的新节点也保留，防止漏检。只在当前 `run_task` 的覆盖中裁剪入口 `next`，不禁用全局节点或改写 Resource，避免影响下一场或其他任务。专属选项后的目标选择链保持不变；本轮不进一步按当前释放者/技能号裁剪，因此同队从者之间的误命中风险仍需后续处理。

验证需覆盖：助战/候补保留、空位、同名不同 ID、形态别名、普通队伍移除全部无关专属项、直接战斗/部分未知/冲突/旧快照完整兜底、分支顺序与用户禁用状态保留，以及连续调用不污染下一场配置。测试结果完成后另行记录，不把离线模拟视为实机验收。

实施验证：`tests/test_battle_special_skill_scope.py` 的 16 项专项回归通过；`tests/component/test_special_skill_scope_framework.py` 用真实 MaaFramework 与拒绝输入的内存控制器，覆盖 7 类场景并跨两个根任务共执行 14 次嵌套调用，验证框架展开的 next 对象可正确裁剪，且不污染父 Context、下一次调用或共享 Resource。构造马嘶/莉莉丝两个分支均可命中的场景时，仅有骑莉莉丝的完整实际队伍会跳过马嘶分支；无快照、未知、冲突或旧快照时恢复原始检测顺序。普通队伍从最多 17 个识别分支减少到 3 个通用识别，末尾 DirectHit 兜底继续保留。

本机 `python tools/run_tests.py --suite unit`、`--suite component`（79 项）及资源/任务 Schema 校验通过。没有缩短原有 0.6 秒、入口 1 秒或弹窗后等待，也没有增加依赖。

同日日服 MaaMCP 实机：按用户选择连接 `127.0.0.1:16384`，从已打开的 5 AP 关卡 PARTY XIII 确认页开始，保留现有从者/礼装，调用正式身份采集和 `auto_battle` 执行一场。六槽均确认（`2800900/304800/202600/2300900/2300500/505500`，助战为第 3 槽），检测范围日志为 `complete_actual_formation`。本队没有已登记的专属弹窗；10 次技能检测的入口均只保留两类不可用弹窗、目标选择及无覆盖层终点，即 3 个通用识别加 DirectHit 兜底。9 次直接释放、1 次通用目标选择（从者 1），未检查队外马嘶/骑莉莉丝等分支，4 回合返回 `ok=True, reason=victory`。最终截图为日服战利品/下一步页面，未继续出击，未修改编队、使用苹果或复活，MCP Agent/客户端与连接均已清理。

## 1. 目标与范围

本轮补齐当前原生自动战斗完全没有处理的 `SelectAddInfo` 技能，在日服实机采集
`1280×720` 现场截图和选项模板，并用构造的战斗动作验证技能能够正常释放、选择默认项、
返回战斗主界面并完成副本。

Chaldea 中的 10 个未覆盖技能定义实际对应 8 名可编成从者。`505700` 是普勒拉蒂的另一
灵基，`1002100` 是芙萝拉的内部变体，不应当当作两名额外从者单独编队。此前把
`1002100` 解释成哈桑·萨巴赫是不正确的，本轮按芙萝拉同一从者处理。

本轮对象如下：

| 从者 | svtId / 技能 | 全部选项 | 固定默认值 |
|---|---|---|---|
| 马嘶 | `203300` / S1 | 无敌、毅力 | 无敌（index 0） |
| 梵高〔矿工〕 | `305600` / S1 | Quick、Arts、Buster | Arts（index 1） |
| 莉莉丝 | `405900` / S3 | 不附加、附加宝具后自身即死 | 不附加（index 0） |
| 普勒拉蒂 | `505600/505700` / S1 | 不更换灵基、更换灵基 | 不更换（index 0） |
| 夏洛特·科黛 | `603800` / S3 | Arts、暴击威力、宝具威力 | Arts（index 0） |
| 芙萝拉 | `1002000/1002100` / S3 | 通常状态、冥界花园状态 | 通常状态（index 0） |
| 安哥拉曼纽 | `1100100` / S3 | 无毅力、50% 恢复、1 HP 恢复 | 50% 恢复（index 1） |
| 但丁·阿利吉耶里 | `2801000` / S2 | 天国化 Arts、地狱化 Buster | 天国化 Arts（index 0） |

固定值只负责在尚未接入 `skillActSelectSelections` 时保证流程可继续，不代表最终推荐策略。
所有选项都要建立独立节点，后续接入配置时只需通过 `pipeline_override` 调整启用项或优先级。

## 2. 实现结构

每个选项建立一个可独立覆盖的识别/点击节点，入口只挂固定默认项：

```text
战斗_特殊技能处理
├── 战斗_<从者><技能号>技能_<固定默认项>选择
└── ……

战斗_<从者><技能号>技能_<其他项>选择  # 节点保留，默认入口不启用
```

- 已采集到实机图的选项使用按钮模板，并点击匹配位置；模板 ROI 只覆盖该按钮所在区域。
- 受持有/强化进度限制、尚未取得模板的选项，临时使用 Chaldea 原始日文按钮文案和固定按钮
  ROI 做 OCR 安全识别，不能伪造模板或宣称实机通过。
- 每组只有固定默认项挂入 `战斗_特殊技能处理.next`。非默认节点仍完整保留，供后续配置
  override 使用。
- 选完后统一接 `战斗_技能目标子屏`、`战斗_特殊技能_已回主界面`，兼容后续目标选择。
- 新增节点的 `doc` 记录日服截图、ROI、默认值和实机结果。
- 所有技能内选项分支必须排在通用 `战斗_技能目标子屏` 前面。目标子屏 OCR 接受宽泛的
  `選択`，若顺序相反，会把技能内选项标题误判成目标选择并点击错误位置。

按[识图美术资源目录约定](识图美术资源目录约定.md)，日服截图裁出的正式模板默认放在 `base`。本轮技能内选项模板放在：

```text
assets/resource/base/image/battle/skill/
```

完整现场截图是验证证据，不进入正式资源包，保存在：

```text
.workbuddy/runtime/maa-mcp-data/evidence/special_skill_options/<svtId>/
```

可实机触发的每个技能至少保存：

- `full_1280x720.png`：选项弹窗完整截图；
- 正式模板：从完整截图按 ROI 无缩放裁出，放入 `assets/resource/base/image/battle/skill/`；
- `after_default.png`：点击默认项并回到战斗主界面后的截图；
- 日志中的模板最高分、阈值、命中节点和点击坐标。

## 3. 执行顺序

### 阶段 A：静态准备

1. 校验 Chaldea 的 `SelectAddInfo`、`skillSvts`、按钮顺序和条件。
2. 确认 8 名从者在本地从者目录、日服账号持有数据和编队模板中的可用性。
3. 为 8 个弹窗建立完整节点清单、资源文件名和默认值，不先伪造模板。
4. JSON 解析和工程 schema 校验必须通过。

### 阶段 B：MaaMCP 实机采集

1. 每次新会话先调用 `find_adb_device_list`；只有一个设备时连接，多个设备时停止等待选择。
2. 连接后立即 `screencap`，确认是日服 FGO 且入口可安全恢复。
3. 使用现有自动编队能力，每轮最多放入 3 名目标从者；未持有者记录为阻塞，不用相似从者替代。
4. 从主界面进入迦勒底之门，选择当日修炼场最低档。导航必须识别入口和 AP/难度，不盲点。
5. 战斗开始后依次点击目标技能；弹窗稳定后先保存 `1280×720` 全屏，再裁出所有选项模板。
6. 点击文档约定的默认项，截图确认回到主界面；继续完成战斗并退出副本。
7. 遇到识别失败、未知弹窗、AP/苹果确认、队伍不合法或从者未持有时，先保存现场并停止该分支。
8. 每轮结束都调用 `stop_pipeline`，避免残留任务继续操作设备。

### 阶段 C：正式实现

1. 将实机裁出的日服模板加入 `resource/base/image/battle/skill`。
2. 把全部选项节点和每组唯一的默认项写入 `自动战斗_特殊技能.json`。
3. 增加静态测试，至少验证：入口包含每组唯一默认项、全部选项节点存在、
   图片存在、库库尔坎等既有分支顺序不变。
4. 运行 JSON/schema、相关 Python 单测和资源引用检查。

### 阶段 D：构造数据实战验证

1. 为每一轮构造只包含必要技能动作的本地战斗数据，明确槽位、技能号和目标。
2. 使用正式原生自动战斗入口执行，不用临时坐标脚本替代特殊技能流水线。
3. 日志必须命中目标父节点和默认选项节点，不能落入 `战斗_特殊技能_无覆盖层`。
4. 技能释放后必须回到 `MAIN_BATTLE`；随后完成关卡并回到结算/主界面。
5. 保存每个从者的通过、失败或未覆盖原因，不把“pipeline succeeded”单独视为通过。

## 4. 通过标准

- 8 名从者、10 个技能定义都有明确节点归属；同一从者的内部变体复用同一弹窗模板时有记录。
- 19 个二选一/三选一按钮都有独立节点；已生成的正式图片模板必须全部来自日服真实
  `1280×720` 截图，无缩放重绘。
- 每个弹窗保留全屏证据，模板 ROI 可从证据图复现。
- 默认项稳定命中并使技能完成；未知弹窗不会被“无覆盖层”误判后静默超时。
- 构造数据实战至少各触发一次目标技能；可编成的批次完成战斗并退出。
- 未持有、技能未开放或当天副本/职阶限制导致无法验证的对象明确标为“未覆盖”，不宣称通过。
- 最终 `git diff` 不混入用户现有的 `assets/interface.json` 等无关修改。

## 5. 风险与恢复

- 日服账号不一定持有全部 8 名从者；先做只读持有清单核对，再决定批次，不能通过抽卡或借用
  不可控助战补齐。
- 安哥拉曼纽和部分新从者可能因等级、灵基或技能强化条件看不到目标技能；此时保留编队/技能页
  证据并停止该对象。
- 低级修炼场仍会消耗 AP；只进入完成采集所需的最少次数，不使用圣晶石恢复 AP。
- 编队修改会保存到游戏的当前队伍。每轮结束记录最终队伍；发生中断时通过 MaaMCP 恢复到可识别
  页面，不使用窗口控制或直接 ADB 点击。
- 采集期间若出现维护、更新、通信错误或非目标弹窗，立即截图并停止后续自动点击。

## 6. Chaldea 数据结构共同点

本轮 10 个技能定义的 `script.SelectAddInfo` 结构完全一致：

```json
{
  "title": "选项弹窗标题",
  "btn": [
    {"name": "按钮文案", "conds": [{"cond": "NONE"}]}
  ]
}
```

- `title` 是弹窗标题，`btn` 数组顺序就是 `skillActSelectSelections` 使用的选项 index。
- 本轮全部按钮条件都是 `NONE`；梵高“至少 10 星才能用”属于技能本体的使用条件，不在
  `SelectAddInfo.btn[].conds` 中。
- UI 只有二选一（马嘶、莉莉丝、普雷拉蒂、芙萝拉、但丁）和三选一（矿工梵高、夏洛特、
  安哥拉曼纽）两种布局。
- 业务语义可归为：防御效果、卡色、是否附加状态、形态切换、伤害增益、毅力档位；数据层
  没有不同的联合类型，全部复用同一 `title + btn[] + conds[]` 容器。
